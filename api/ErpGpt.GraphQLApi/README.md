# ErpGpt.GraphQLApi

A **read-only** GraphQL API over the AdventureWorks ERP database.
.NET 10 · HotChocolate 16 · EF Core 10 · PostgreSQL 16

16 endpoints. Every list endpoint carries pagination, filtering, sorting,
column selection and nested includes, so a small API surface answers a large
number of questions.

---

## Run it

```bash
# 1. database  (from api/)
cd .. && docker compose up -d

# 2. the API   (from api/ErpGpt.GraphQLApi/)
dotnet run
```

That is all — no flags needed. It starts on **http://localhost:5000** in the
Development environment.

| URL | What it is |
|---|---|
| http://localhost:5000/graphql | The GraphQL IDE — write queries, browse the schema |
| http://localhost:5000/health | `{"status":"healthy","database":"connected"}` |

## Verify it

With the API running, in a second terminal:

```bash
./verify.sh
```

It exercises all 16 endpoints plus the guard rails and prints a pass/fail
line for each — 18 checks in total. Point it elsewhere with
`API=http://localhost:5100 ./verify.sh`.

To confirm the *numbers* rather than just that endpoints respond, compare an
aggregation against SQL directly:

```bash
# the API's answer
curl -s -X POST http://localhost:5000/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{ salesSummary(from:\"2022-01-01\", to:\"2025-12-31\"){ totalRevenue orderCount customerCount } }"}'

# the database's answer — these must match
docker exec api-db-1 psql -U erpgpt -d erpgpt -c \
  "SELECT sum(totaldue), count(*), count(DISTINCT customerid) FROM sales.salesorderheader;"
```

Both return **123216786.1159**, **31465**, **19119**.

> **Only one container may mount the `api_pgdata` volume at a time.** Two
> Postgres servers on one data directory corrupt each other's reads.
>
> Port 5432 must be free. If another project is using it, stop that container
> or change the port in both `docker-compose.yml` and `appsettings.json`.

## The four abilities

These are the whole point of the design. Every list endpoint has all four.

| Ability | How you write it | What it does |
|---|---|---|
| **Pagination** | `skip: 0, take: 25` | Offset paging. Returns `totalCount` for page numbers. Hard cap: 100 rows. |
| **Filtering** | `where: { ... }` | The WHERE clause. Reaches through relationships. |
| **Sorting** | `order: [{ field: ASC }]` | One or more sort keys. |
| **Column selection** | Just list the fields | Only the columns you name are read from the database. |
| **Includes** | Nest the relationship | Joined into the **same** query — no N+1. |

### One query using all of them

```graphql
{
  orders(
    skip: 0
    take: 3
    where: { totalDue: { gt: 10000 } }
    order: [{ totalDue: DESC }]
  ) {
    totalCount                       # 1878

    items {
      salesOrderId  orderDate  totalDue

      customer {                     # include: order -> customer
        displayName
        territory { name group }     # include: -> territory
      }

      lines {                        # include: order -> lines
        orderQty  unitPrice  lineTotal
        product { name productNumber }
      }
    }
  }
}
```

### Filter operators

`eq` `neq` `gt` `gte` `lt` `lte` `in` `nin` `contains` `startsWith` `endsWith`,
combined with `and` / `or`.

```graphql
# customers in Canada
customers(where: { territory: { name: { eq: "Canada" } } })

# bikes between $500 and $1500
products(where: {
  and: [
    { listPrice: { gte: 500 } },
    { listPrice: { lte: 1500 } },
    { subcategory: { category: { name: { eq: "Bikes" } } } }
  ]
})

# orders in a date range
orders(where: { orderDate: { gte: "2024-01-01T00:00:00Z" } })
```

## The 16 endpoints

### Browse — 7

All support `skip` / `take` / `where` / `order`.

| Endpoint | Example |
|---|---|
| `customers` | `{ customers(take: 5) { totalCount items { customerId displayName isStore } } }` |
| `orders` | `{ orders(take: 5, order: [{ orderDate: DESC }]) { items { salesOrderId totalDue } } }` |
| `orderLines` | `{ orderLines(where: { productId: { eq: 782 } }, take: 5) { totalCount items { orderQty lineTotal } } }` |
| `products` | `{ products(where: { color: { eq: "Black" } }, take: 5) { items { name listPrice } } }` |
| `productCategories` | `{ productCategories { items { name subcategories { name } } } }` |
| `territories` | `{ territories { items { name group countryRegionCode } } }` |
| `salesPeople` | `{ salesPeople { items { businessEntityId person { fullName } salesQuota } } }` |

### Detail — 3

| Endpoint | Example |
|---|---|
| `customer(id)` | `{ customer(id: 29641) { displayName orders { salesOrderId totalDue } } }` |
| `order(id)` | `{ order(id: 51131) { orderDate totalDue lines { orderQty product { name } } } }` |
| `product(id)` | `{ product(id: 782) { name listPrice subcategory { category { name } } } }` |

### Aggregations — 6

Dates are plain `"2024-01-01"`. `to` includes the whole day.
The grouping happens in Postgres, not in the API.

```graphql
# How much did we sell, and to how many customers?
{ salesSummary(from: "2024-01-01", to: "2024-12-31") {
    totalRevenue orderCount averageOrderValue customerCount } }

# Who are our biggest customers?
{ topCustomers(from: "2024-01-01", to: "2024-12-31", limit: 5) {
    customerName territory revenue orderCount } }

# What sells best?
{ topProducts(from: "2024-01-01", to: "2024-12-31", limit: 5) {
    productName productNumber category revenue unitsSold } }

# Trend over time — MONTH, QUARTER or YEAR
{ revenueByPeriod(from: "2024-01-01", to: "2024-12-31", interval: QUARTER) {
    label revenue orderCount } }

# Which region sells most?
{ salesByTerritory(from: "2024-01-01", to: "2024-12-31") {
    territory group revenue orderCount } }

# Revenue split by category
{ salesByCategory(from: "2024-01-01", to: "2024-12-31") {
    category revenue unitsSold } }
```

## Things that will surprise you about this data

- **A customer has no name column.** `sales.customer` points at *either* a
  person *or* a store. Use `displayName`, which resolves whichever applies.
- **Every order has `status = 5` (Shipped).** There are no cancelled, pending
  or rejected orders in this database, so status breakdowns are not
  meaningful here.
- **Orders run 30 May 2022 – 29 June 2025** and total **$123,216,786.12**
  across 31,465 orders. Customer ids in orders start at **11000** — customers
  1–10999 exist but have never ordered.
- **`totalDue` is stored**, not computed, so revenue is a plain `SUM`.
- **`product.orderLines` is deliberately not exposed.** One product can appear
  on 4,688 order lines. Use the paged top-level endpoint instead:
  `orderLines(where: { productId: { eq: 782 } })`.

## Guard rails

| Rule | Where |
|---|---|
| Read-only — there are no mutations | by design |
| Max 100 rows per page (default 25) | `Program.cs` → `ModifyPagingOptions` |
| Max query depth 12 | `Program.cs` → `AddMaxExecutionDepthRule` |
| Max query cost 2000, checked before execution | `Program.cs` → `ModifyCostOptions` |
| 30-second execution timeout | `Program.cs` → `ModifyRequestOptions` |
| Ranking `limit` clamped to 100 | `Query.Aggregations.cs` → `Cap()` |
| Errors carry codes (`INVALID_DATE_RANGE`, …) | `ErpErrorFilter.cs` |
| Introspection is off outside Development | HotChocolate default |
| EF never creates or migrates the schema | `ErpDbContext.cs` — no `EnsureCreated`, no seeder |

## Directory structure

Three folders, and each one has a single job. If you are looking for where a
change belongs, the rule is: **Domain** describes the tables, **Data** connects
them to Postgres, **GraphQL** decides what the outside world may ask for.

```
ErpGpt.GraphQLApi/
│
├── Program.cs                        79   Startup: DI, GraphQL server, guard rails, /health
├── ErpGpt.GraphQLApi.csproj               net10.0 + the four packages
├── appsettings.json                       Connection string, log levels
├── appsettings.Development.json           Turns on SQL logging
├── Properties/
│   └── launchSettings.json                Port 5000 + Development environment
│
├── Domain/                                WHAT THE DATA IS
│   │                                      Plain C# classes. No attributes that
│   │                                      tie them to a database or to GraphQL,
│   │                                      apart from descriptions.
│   ├── Sales/SalesEntities.cs       178   Customer, Store, SalesPerson, Territory,
│   │                                      SalesOrder, SalesOrderLine
│   ├── Production/ProductionEntities.cs 81 Product, ProductSubcategory, ProductCategory
│   └── People/PeopleEntities.cs      59   Person, Address, StateProvince
│
├── Data/                                  HOW IT REACHES POSTGRES
│   └── ErpDbContext.cs              153   Maps the 12 classes onto AdventureWorks
│                                          tables. Never creates or migrates.
│
├── GraphQL/                               WHAT CALLERS MAY ASK FOR
│   ├── Query.Browse.cs               79   The 7 list + 3 detail endpoints
│   ├── Query.Aggregations.cs        245   The 6 aggregation endpoints
│   ├── CustomerNameDataLoader.cs     48   Batches customer name lookups
│   ├── ErpErrorFilter.cs             46   Turns exceptions into readable errors
│   └── Types/
│       ├── AggregateResults.cs       63   Return shapes for aggregations
│       └── EntityTypes.cs            73   Per-type tweaks (projection, hidden fields)

├── API.md                                 Every endpoint's request payload + response
├── requests.http                          Click-to-run requests for the IDE
├── ErpGpt.GraphQLApi.postman_collection.json
└── verify.sh                              18 checks against a running API
```

`Query.Browse.cs` and `Query.Aggregations.cs` are two halves of the **same**
`Query` class — C# `partial` classes. They are split only so browsing code and
maths code do not crowd each other; to GraphQL it is one type.

## How the application works

### The shape of it

```
     HTTP POST /graphql
            │
            ▼
   ┌─────────────────┐   rejects bad queries BEFORE touching the database:
   │   Validation    │   unknown fields · depth > 12 · cost > 2000
   └────────┬────────┘   → HTTP 400, nothing runs
            │
            ▼
   ┌─────────────────┐   Query.Browse.cs      → returns IQueryable (not yet run)
   │    Resolver     │   Query.Aggregations.cs → runs its own tuned LINQ
   └────────┬────────┘
            │
            ▼
   ┌─────────────────┐   paging, where, order and column selection are
   │   Middleware    │   layered onto the IQueryable as a query PLAN
   └────────┬────────┘
            │
            ▼
   ┌─────────────────┐   EF Core translates the finished plan to SQL
   │   ErpDbContext  │   ONE statement — filter, sort, limit and joins included
   └────────┬────────┘
            │
            ▼
       PostgreSQL          + one COUNT for totalCount
            │              + one batched DataLoader query if displayName was asked for
            ▼
        JSON response
```

### Why browse endpoints are only one line each

This is the idea the whole API rests on. A browse resolver returns an
`IQueryable` — a *description* of a query that has not run yet:

```csharp
[UseOffsetPaging(MaxPageSize = 100, IncludeTotalCount = true)]
[UseProjection, UseFiltering, UseSorting]
public IQueryable<Customer> GetCustomers(ErpDbContext db) => db.Customers;
```

Each attribute is middleware that edits that description before it executes:

| Attribute | What it adds to the query |
|---|---|
| `UseFiltering` | the caller's `where` becomes a SQL `WHERE` |
| `UseSorting` | the caller's `order` becomes `ORDER BY` |
| `UseOffsetPaging` | `skip`/`take` become `OFFSET`/`LIMIT`, plus a `COUNT` |
| `UseProjection` | the fields requested become the `SELECT` list |

Only after all four have had their say does EF turn it into SQL. That is why
asking for three columns reads three columns, and why a nested `customer { territory { name } }`
becomes a `JOIN` in the *same* statement instead of extra round trips.

So the endpoint count stays at 16 while the number of answerable questions
does not — the caller composes the question, and the database does the work.

### Why aggregations are written differently

Aggregations do **not** return `IQueryable`. Summing 31,465 orders by handing
the caller a filterable list would be slow and easy to get wrong, so each one
runs its own LINQ and returns a finished answer:

```csharp
public async Task<List<TerritorySales>> GetSalesByTerritory(
    ErpDbContext db, DateOnly from, DateOnly to)
```

The caller chooses an endpoint and passes dates. They cannot change how the
total is computed — which is exactly what you want when an AI layer is writing
the queries.

### Start-up, in the order it happens

`Program.cs` reads top to bottom:

1. **Register the DbContext factory** with the connection string, in
   no-tracking mode — the API never writes, so EF should not keep change
   snapshots of everything it reads.
2. **Build the GraphQL schema** from the `Query` class. HotChocolate reflects
   over the methods and the entity classes they return, and generates the
   schema — the filter and sort input types are derived from your properties,
   which is why nobody hand-writes them.
3. **Apply per-type rules** from `Types/EntityTypes.cs` (below).
4. **Fit the guard rails**: page cap, depth, cost ceiling, timeout, error filter.
5. **Map the endpoints**: `/graphql` and `/health`.

### The three files that carry the surprises

Most of the code is unremarkable. These are the parts worth reading before you
change anything:

**`Data/ErpDbContext.cs`** — one loop at the bottom lowercases every table and
column name, because AdventureWorks uses `salesorderid` rather than
`SalesOrderId`. That single rule replaces roughly 120 lines of
`HasColumnName()`. It also pins every date column to
`timestamp without time zone`; without that, Npgsql assumes `timestamptz` and
shifts your values.

**`GraphQL/Types/EntityTypes.cs`** — where projection gets corrected.
Projection reads only the columns asked for, which breaks computed fields
whose inputs nobody selected. Fields built from plain columns (`lineTotal`,
`isCurrentlySold`, `fullName`) are fixed with `IsProjected(true)`. This file is
also where `product.orderLines` is hidden, because one product can appear on
4,688 lines.

**`GraphQL/CustomerNameDataLoader.cs`** — a customer has no name column; the
name is in either the linked store or the linked person. `IsProjected` does not
work for relationships, so `displayName` is resolved here instead. HotChocolate
collects every customer id in the page and asks for all their names in **one**
query, so a 100-row page costs one extra statement rather than 100.

### The one rule to follow when adding an aggregation

Group into an **anonymous type first**, then map to the record. EF Core cannot
translate a record constructor inside `GroupBy().Select()` — it throws
outright. Written the wrong way round, a "fix" that makes the exception go away
is usually `.ToList()` in the middle, which quietly drags every row into memory
and looks fine until the data grows.

```csharp
// works — GROUP BY runs in Postgres
.GroupBy(o => o.OrderDate.Year)
.Select(g => new { Year = g.Key, Revenue = g.Sum(x => x.TotalDue ?? 0m) })
.ToListAsync();                          // ← SQL ends here

// then, in memory, over a handful of grouped rows:
rows.Select(r => new PeriodRevenue(r.Year, 1, $"{r.Year}", r.Revenue, r.Count))
```

Check your work by watching the SQL (below) — you should see `GROUP BY` in the
statement. If you see a plain `SELECT` of every row instead, the grouping
escaped to C#.

## Adding an endpoint

1. **A new list?** Add one method to `Query.Browse.cs` with the four
   attributes. Nothing else is needed — filter and sort inputs are generated
   from the entity.
2. **A new figure?** Add a method to `Query.Aggregations.cs` plus a record in
   `Types/AggregateResults.cs`, following the grouping rule above.
3. **A new table?** Add the class under `Domain/`, map it in `ErpDbContext.cs`,
   and expose it in step 1.
4. Add the payload to `API.md` / `requests.http`, and a check to `verify.sh`.
5. Confirm the number against SQL before you call it done — that is how every
   figure in this API was signed off.

## Watching the SQL

In Development, EF logs every statement it runs, so you can see exactly what
your GraphQL turned into. A 100-row page with `displayName` costs three
statements: the page, the count, and one batched name lookup.

`appsettings.Development.json` is gitignored (repo convention), so it will not
exist after a fresh clone. Create it to turn SQL logging on:

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.EntityFrameworkCore.Database.Command": "Information"
    }
  }
}
```

Set that last value to `Warning` to quieten it again. Note that every value
under `LogLevel` must be a valid level — a `"//"` comment key will crash
start-up.
